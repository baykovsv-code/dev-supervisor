# Руководство оператора Development Supervisor

Это поддерживаемое русское руководство для оператора. Нормативным источником остаётся
[английское руководство](operator-guide.md): если тексты различаются, действует
английский. Проверка перевода следит за парой, ссылками и свежестью исходника, но не
утверждает смысловую эквивалентность; правила описаны в
[документации по управлению документацией](documentation-governance.md).

## Установка и первое знакомство

Нужны Python 3 и Git. Для запуска модели также нужны настроенный Codex CLI и явное
разрешение по квоте. Linux — квалифицированная платформа. На настоящем компьютере Mac
этот релиз не проверяли, поэтому macOS не поддерживается.

Из рабочей копии движка инициализируйте управляемый репозиторий:

```bash
./supervisor init /path/to/project
cd /path/to/project
./dev status
```

Если уже есть проверенная политика, укажите её явно: `./supervisor init
/path/to/project --policy /path/to/policy.json`. Инициализация создаёт исполняемый
launcher `dev`, отслеживаемый файл `dev-supervisor.json`, игнорируемый каталог runtime
`.dev-supervisor/` и, только для стандартной настройки, минимальный план с заготовкой
тикета. Существующие конфликтующие управляющие файлы не перезаписываются. Перед первым
запуском проверьте и закоммитьте созданные отслеживаемые файлы.

Если рабочая копия движка перемещена, задайте `DEV_SUPERVISOR_HOME` для локальной
привязки программы запуска. Не исправляйте привязку ручным редактированием файлов
исполняемой среды.

## Ментальная модель

Есть четыре границы:

1. Рабочая копия движка содержит контроллер, подсказки, схемы, тесты и руководства.
2. Управляемый репозиторий содержит файлы продукта, политику, планы, тикеты и
   программу запуска.
3. В игнорируемом `.dev-supervisor/` лежат локальное состояние, блокировки,
   наблюдения квоты и свидетельства запуска.
4. Настроенный удалённый репозиторий — лишь цель сохранения; он не является ни
   блокировкой, ни источником полномочий.

У управляемого репозитория может быть только один пишущий процесс и одно активное
неизменяемое поколение движка. `status` ничего не меняет. Неожиданные ветка, HEAD,
тикет, идентификатор движка, контрольная характеристика рабочего дерева, версия
политики или шлюз означают: остановитесь.

Обычный ход работы идёт от проверки и утверждённого планирования к `READY`, работе над
тикетом, проверке, локальному коммиту и контролируемой остановке. Завершение плана не
выбирает и не запускает новую работу. Неизвестное состояние, квота, принадлежность,
платформа, совместимость или протокол никогда не дают разрешения.

## Обычная работа

Перед вызовом модели проверьте состояние и внесите текущее достоверное наблюдение:

```bash
./dev status
./dev quota set --five-hour <percent> --weekly <percent>
./dev run
```

`./dev resume` используйте только после чтения статуса, шлюза и показанной инструкции
по восстановлению. Наблюдение квоты разрешает только ограниченный политикой вызов: оно
не утверждает архитектуру, не открывает шлюз, не включает возможность и не разрешает
отправку изменений. Не угадывайте проценты и время сброса. Если автоматическое
наблюдение недоступно или неоднозначно, оно не даёт разрешения: внесите текущее
достоверное значение явной командой выше либо остановитесь.

После запуска проверьте:

```bash
./dev status
git status --short --branch
git log --oneline --decorate -5
```

Обычно проверенный коммит реализации создаёт Supervisor. Не делайте заранее commit,
amend, rebase, squash, reset, clean или stash для сохранённой контрольной точки.
Добавлять точные пути в индекс можно только для документированного действия человека в
состоянии покоя.

## Шлюзы и безопасная остановка

`HUMAN_GATE` и `PERIODIC_CHECKPOINT` — успешные контролируемые остановки. Они не
означают, что `resume` разрешён. Если статус показывает `resume_command: null`,
обычная команда resume обязана оставить шлюз закрытым. Проверьте требуемые
свидетельства, план, дерево, завершённые тикеты и тесты; открывайте шлюз только
документированной командой и с содержательной заметкой.

Остановиться безопасно можно так:

```bash
./dev stop
./dev status
```

Не выключайте систему, пока активны модель, проверка, контроль области изменений или
коммит. Если статус сообщает о контрольной точке в состоянии покоя или об уже
спокойной остановке, таких процессов нет. При неожиданном условии сохраните вывод
статуса и свидетельства исполняемой среды.

| Сигнал | Что означает | Безопасное действие |
|---|---|---|
| `READY` | Следующее проверенное действие может быть доступно. | Перед `run` или `resume` снова проверьте тикет, дерево и квоту. |
| `HUMAN_GATE` / `PERIODIC_CHECKPOINT` | Нужна проверка человеком. | Не обходите шлюз; следуйте документированной процедуре открытия. |
| квота заблокирована или неизвестна | Нет разрешения на вызов. | Внесите свежее достоверное ручное наблюдение либо остановитесь. |
| `VERIFICATION_FAILED` | Детерминированная проверка не прошла. | Сохраните журнал; используйте только предложенный явный маршрут восстановления в том же тикете. |
| `SCOPE_BLOCKED`, `GIT_BLOCKED` или конфликт владения | Защита остановила небезопасное действие. | Не меняйте состояние и не принуждайте Git; разберите причину указанным процессом. |
| `SUPERVISOR_REPAIR_FAILED` | Ремонт контроллера не был разрешён или не завершился безопасно. | Сохраните свидетельства и используйте отдельно утверждённое изменение контроллера. |

## Восстановление и расширенные условия

Восстановление опирается на свидетельства. Не удаляйте блокировки, записи квоты,
артефакты запусков, привязки, архивы или состояние, чтобы заставить команду продолжить
работу. Для неизменённой общей контрольной точки `VERIFICATION_FAILED` только явно
предложенный и проверяемый маршрут восстановления в том же тикете может сверить точную
контрольную точку, одну текущую неудачную проверку и её сохранённый журнал. Эта сверка
не вызывает модель и не расходует квоту; последующее исправление обязано пройти все
проверки, контроль области изменений и шлюзы коммита.

`./dev recover-protected-snapshot` — узкая команда для исторического дефекта, а не
общий обход защиты. Используйте её лишь когда условия в статусе доказывают дефект
защищённого снимка управляющих файлов: команда сверяет тикет, запуски, HEAD, ветку,
байты изменённых файлов, отчёты, артефакты, проверку квоты, снимок продукта и полную
контрольную характеристику Git. Любое несовпадение оставляет контрольную точку без
изменений.

Обновление движка готовится как отдельное неизменяемое поколение. Проверяйте
идентификатор, совместимые версии, пробный переход и тесты вне активного контроллера;
переключайте только в состоянии покоя с архивом, затем выполняйте сверку без записи.
Устаревший хост или неподдерживаемое состояние ничего не записывают. Откат сначала
останавливает новое поколение, затем документированной командой восстанавливает
архивного предшественника. Храните архивы и квитанции восстановления: очистка текущей
документации их не удаляет.

Переход со старой версии выполняется только по явному решению и сначала репетируется
на изолированной копии. Нужны поддерживаемый источник в состоянии покоя, явный
пробный переход, зафиксированная контрольная сумма источника, решение человека
«выполнять/не выполнять» и сверка без записи после передачи привязки. При отказе
остановите кандидата в состоянии покоя и выполните документированный откат. Никогда
не редактируйте вручную архив, привязку, политику, состояние, журнал квоты или
блокировку, чтобы принудить переход либо откат.

## Полномочия, коммиты и отправка изменений

Конфигурация имеет версию и проходит проверку до запуска модели, изменения Git или
операции с удалённым репозиторием. `self_modification`,
`user_requested_modification` и `repository_push` независимы и по умолчанию
отключены. Содержимое репозитория может ограничить разрешение хоста, но не может его
включить. Некорректная, противоречивая, отсутствующая или неизвестная конфигурация
останавливает работу без разрешения.

Проверенный коммит тикета остаётся локальным, пока отдельно включённая возможность
отправки не подтвердит его в настроенном удалённом репозитории и ветке. Не выводите
полномочие из настроек Git по умолчанию или политики репозитория. Не используйте
force-push и не переписывайте историю. Ошибка отправки сохраняет локальный коммит и
не означает завершённого сохранения.

## Полезные привычки

- Перед каждой существенной командой читайте `./dev status`.
- Сохраняйте единственный пишущий процесс и не считайте синхронизацию Git блокировкой исполняемой среды.
- Берегите контрольные точки и свидетельства; не используйте очистку для сокрытия несовпадения.
- Остановитесь, если запрос расширяет область работы или меняет архитектуру без утверждения.
- Не включайте в коммиты учётные данные, данные учётной записи, артефакты исполняемой среды и неотредактированные свидетельства.
- После проверенного обновления руководств запускайте `python3 scripts/check_documentation.py`.

За деталями политики и реализации обращайтесь к проверенным документам, указанным
активными планом и тикетом. Исторические материалы 1.x и завершённые материалы 2.0
сохраняются в истории Git и не являются текущей инструкцией оператора.
